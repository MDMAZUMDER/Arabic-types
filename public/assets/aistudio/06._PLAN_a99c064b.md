# Sequential Development Plan

## Arabic Typing Learning App

**Status:** Draft v1.0

Build in the following order. Do not expand scope beyond the three
approved feature groups without explicit approval.

## Phase 1 --- Confirm product rules

1.  Approve the PRD scope.
2.  Finalize exact no-mistake completion and retry behavior.
3.  Finalize how backspace/corrections affect mistake and accuracy
    calculations.
4.  Confirm whether the first release must be fully offline.
5.  Select the Android framework and database.

**Exit criteria:** Product rules and technology choices are written
down; no unresolved behavior affects core typing logic.

## Phase 2 --- Project foundation

1.  Create the app project and pin framework/tool versions.
2.  Establish typography, colors, spacing and component tokens from
    `TOKENS.md`.
3.  Set up RTL support and Arabic font rendering.
4.  Add local persistence.
5.  Create a basic navigation shell.

**Exit criteria:** App launches on target Android device sizes; Arabic
text renders correctly in RTL.

## Phase 3 --- Built-in Arabic keyboard

1.  Implement the agreed Arabic key layout.
2.  Implement key press handling.
3.  Implement key states: default, pressed, highlighted and disabled.
4.  Verify touch accuracy and small-screen layout.

**Exit criteria:** User can enter Arabic text using the in-app keyboard.

## Phase 4 --- Typing engine and learning modes

1.  Implement target text and expected-character pointer.
2.  Implement Guided Mode highlighting.
3.  Implement Hint Mode behavior.
4.  Implement Test Mode without hints/highlighting.
5.  Implement strict error handling: wrong input never advances the
    expected position.
6.  Add automated tests for correct input, wrong input, retries and mode
    restrictions.

**Exit criteria:** All three modes behave exactly as defined in
`STATE.md`.

## Phase 5 --- Curriculum and unlocking

1.  Add individual-letter lessons.
2.  Add combinations using learned letters.
3.  Add small, medium and longer words.
4.  Add short and longer sentences.
5.  Implement sequential stage unlocks.
6.  Verify that a mistake blocks clean completion and progression.

**Exit criteria:** Learner cannot skip ahead without meeting the current
stage's completion rule.

## Phase 6 --- Reports

1.  Record attempt start/end time.
2.  Record correct input and mistakes.
3.  Calculate accuracy and typing speed.
4.  Identify commonly missed Arabic characters.
5.  Display the report after the exercise/test.
6.  Persist attempt history for comparison where included.

**Exit criteria:** Report calculations are tested and match recorded
attempt data.

## Phase 7 --- UI polish and quality assurance

1.  Apply consistent professional game-inspired visual design.
2.  Add restrained transitions and clear visual feedback.
3.  Test light/dark themes if included in the selected scope.
4.  Test Arabic RTL, mixed text, punctuation and keyboard behavior.
5.  Test on small and larger Android screens.
6.  Fix usability, performance and accessibility issues.

**Exit criteria:** Core flows are stable, legible and consistent across
target devices.

## Phase 8 --- Release preparation

1.  Verify all acceptance criteria in `PRD.md`.
2.  Verify state transitions against `STATE.md`.
3.  Verify data fields and report calculations against `SCHEMA.md`.
4.  Record exact dependency and SDK versions in `STACK.md`.
5.  Prepare signed Android release build.

**Exit criteria:** Release candidate passes the agreed test checklist.

## Change control

-   Any new feature requires explicit user approval and a PRD update.
-   If a decision changes, update the relevant Vault file first.
-   Keep `CLAUDE.md` aligned with all six Vault files; do not claim a
    live bidirectional connection unless it is actually configured and
    verified.
