# Technology Stack
## Arabic Typing Learning App

**Status:** Proposed baseline v1.1  
**Platform:** Native Android  
**Architecture:** Offline-first, single-device initial release

## 1. Selected technology stack

| Layer | Technology | Responsibility |
|---|---|---|
| Programming language | Kotlin | Main application language |
| Android UI | Jetpack Compose | Screens and interactive UI |
| Design system | Material 3 | UI components and theming |
| Arabic keyboard | Custom keyboard built with Jetpack Compose | In-app Arabic typing keyboard and key highlighting |
| Architecture | MVVM + Repository pattern | Separation of UI, business logic and data |
| Local database | Room | Lessons, learner progress and attempt history |
| Settings storage | DataStore | App preferences and lightweight settings |
| Async processing | Kotlin Coroutines + Flow | Asynchronous work and observable state |
| Navigation | Navigation Compose | App screen navigation |
| Dependency injection | Hilt | Dependency management |
| Unit testing | JUnit | Typing engine, progression and report calculations |
| UI testing | Compose UI Test | Screen and interaction tests |
| Build configuration | Gradle Kotlin DSL | Android build configuration |
| Dependency management | Gradle version catalog (`libs.versions.toml`) | Centralized dependency versions |

## 2. Why this stack
- Kotlin and Jetpack Compose provide a native Android implementation path.
- Compose supports a custom on-screen keyboard with explicit key states and touch behavior.
- Room stores curriculum progress and reports locally.
- DataStore stores small app preferences.
- MVVM and Repository separation keep typing rules independent from UI rendering.
- Coroutines and Flow support responsive UI state updates.
- JUnit and Compose UI Test provide coverage for strict progression and keyboard interactions.

## 3. Architecture modules

### Presentation
- Compose screens
- Arabic keyboard UI
- Screen-level ViewModels
- UI state and events

### Domain
- Typing engine
- Guided, Hint and Test mode rules
- Curriculum progression and unlock rules
- Accuracy, speed and mistake calculations

### Data
- Room entities and DAOs
- DataStore preferences
- Repository implementations
- Curriculum content source

## 4. Offline-first decision
The initial release is designed to work without a backend:
- Lessons are bundled with the app or stored locally.
- Progress and exercise reports are stored in Room.
- Preferences are stored in DataStore.
- No Firebase, cloud database, account system or server is required for the first release.

A backend or synchronization layer must not be added unless the product owner approves it.

## 5. Version policy
The technologies above are the selected baseline. Exact dependency and SDK versions must be checked for compatibility and pinned when the Android project is initialized.

Record exact versions for:
- Kotlin
- Android Gradle Plugin
- Gradle
- Compose BOM
- Material 3
- Room
- DataStore
- Navigation Compose
- Hilt
- Android compile/target SDK

Use stable compatible releases, not preview/beta versions, for the production baseline unless explicitly approved. Store dependency versions centrally in `gradle/libs.versions.toml` and update this file whenever versions change. Do not write unverified version numbers into documentation.

## 6. Important implementation notes
- Use Compose for the in-app learning keyboard; this is not an Android system-wide IME keyboard.
- Verify Arabic shaping, RTL layout, punctuation and cursor behavior on real Android devices.
- Keep the typing engine framework-independent where practical so it can be unit tested.
- Make all mode and stage unlock decisions in domain logic, not directly in composable UI code.
- Keep report formulas consistent with `PRD.md` and `SCHEMA.md`.
